# Physical trainer integration guide

This is the repeatable acceptance procedure for a new FTMS trainer, firmware revision, browser, or operating system. It is intentionally vendor-neutral. A simulator pass is useful for application development but never qualifies physical resistance behavior.

The authoritative protocol target is the Bluetooth SIG [Fitness Machine Service 1.0.1](https://www.bluetooth.com/specifications/specs/fitness-machine-service-1-0-1/). Browser device discovery must run in a secure context and directly from a user gesture, as described by [Chrome's Web Bluetooth documentation](https://developer.chrome.com/docs/capabilities/bluetooth).

## Tonight: shortest safe path

- [ ] Update the trainer firmware, then unplug the trainer for 30 seconds.
- [ ] Secure the bicycle; keep trainer power within reach; do the first control command with nobody riding.
- [ ] Close the vendor app, Zwift, and every other app or head unit that might control the trainer.
- [ ] Use current Chrome or Edge on a laptop with Bluetooth enabled.
- [ ] Run `npm ci`, then `npm run dev`, and open `http://127.0.0.1:4173`.
- [ ] Leave resistance encoding on **FTMS 1.0.1 · modern SINT16** for a current KICKR CORE.
- [ ] Fill manufacturer, exact model, firmware, operating system, and browser fields in **Device qualification**.
- [ ] Acknowledge the safety setup, choose **Connect trainer**, and work through all 12 guided checks.
- [ ] Put requested/observed values in every observation field; a checkbox without evidence cannot pass the release gate.
- [ ] Export the passing report and also download the session log if anything was surprising.

For a first-generation Wahoo KICKR CORE, Wahoo documents that Bluetooth FTMS was added in firmware 1.1.1. Use the newest firmware offered for the exact device; do not apply CORE 2 firmware guidance to a first-generation CORE. See Wahoo's [KICKR CORE firmware release notes](https://support.wahoofitness.com/hc/en-us/articles/360000217839-KICKR-CORE-Firmware-Release-Notes).

## What counts as a device configuration

Compatibility belongs to this full tuple, not merely a marketing name:

| Field                       | Example                  |
| --------------------------- | ------------------------ |
| Manufacturer                | Wahoo                    |
| Model                       | KICKR CORE               |
| Firmware                    | 1.5.36                   |
| Resistance command encoding | FTMS 1.0.1 `sint16`      |
| Browser and version         | Chrome 140               |
| Operating system            | macOS 15                 |
| Library runtime fingerprint | Generated by Trainer Lab |

A firmware or behavioral source change requires a new physical run. A metadata-only package version bump does not: the report contains a SHA-256 fingerprint of the actual library and Trainer Lab runtime sources.

## Before connecting

1. Inspect the bicycle, axle/adapters, trainer feet, cassette, and power cable.
2. Update firmware using the manufacturer's supported application. Fully close that application afterward. Wahoo's own update guidance recommends ensuring the trainer is not connected to other apps or devices and power-cycling after an update.
3. Put the bicycle in a stable gear and make the first resistance command unoccupied.
4. Choose a low target. Do not use a trainer's advertised maximum merely to prove the maximum exists.
5. Know how to cut power immediately. Stop for unexpected braking, heat, smell, noise, or unstable mounting.
6. Do not test while fatigued or use this qualification run as a maximal workout.

## Connection and discovery

1. Select the resistance encoding before connecting:
   - Use `sint16` for FTMS 1.0.1 and current compliant devices.
   - Use `uint8` only for a verified legacy FTMS 1.0 implementation.
2. Choose **Connect trainer** from a direct click. Web Bluetooth will not allow background or automatic device selection.
3. Select only the intended trainer in the browser chooser.
4. Confirm the Lab reaches `ready` and displays capabilities and supported ranges.
5. Do not certify a device with `strictProtocol: false`. Lenient mode is a diagnostic escape hatch for non-conformant devices, not qualification evidence.

Expected core FTMS surface for this library:

- Fitness Machine Service `0x1826`
- Fitness Machine Feature `0x2ACC`
- Indoor Bike Data `0x2AD2`
- Fitness Machine Control Point `0x2AD9`
- Fitness Machine Status `0x2ADA`
- Supported Power Range `0x2AD8` when power target is advertised
- Supported Resistance Level Range `0x2AD6` when resistance target is advertised

## The 12 acceptance checks

### 1. Ten clean connections

Connect, wait for `ready`, disconnect, and repeat ten times without reloading the page. The Lab counter must reach `10 / 10`. Every disconnect must clear capabilities and telemetry; every reconnect must perform fresh discovery.

Record chooser behavior, approximate connection time, failures, duplicate events, and whether a browser reload was needed. Any reload resets the counter and the run.

### 2. Power and cadence telemetry

Pedal gently. Record one plausible power/cadence pair and confirm both respond continuously. Coast and verify both values return toward zero rather than remaining falsely active.

### 3. Acquire control

With other trainer apps closed, choose **Take control**. A passing result has control state `owned` and a successful response for opcode `0x00`.

### 4. Three safe ERG targets

First send a low target while the bicycle is unoccupied and confirm there is no abrupt unsafe brake response. Then ride at three comfortable targets long enough for power to settle. A possible personal test is 80 W, 120 W, and 160 W, but lower these values if they are not easy and safe for the rider.

For each target record requested watts, steady observed watts, cadence, and approximate settling time. Stop if resistance rises unexpectedly as cadence falls.

### 5. Manual resistance

Test the advertised minimum, midpoint, and a safe upper value. Record each requested level and the physical result. Direction must be monotonic: a higher requested level must not feel easier than a lower level under comparable pedaling.

### 6. Simulated grade

Test a small descent, flat, and small climb—for example `-2%`, `0%`, and `+2%`. Record the grades and physical response. Do not start with extreme grades.

### 7. Start, pause, resume, and reset

Run this state sequence and record exactly what Trainer Lab shows:

`idle → running → paused → running → reset → idle`

Reset must also move control to `unavailable`; take control again before later command tests.

### 8. Primary stop

While running at a low target, choose **Stop resistance**. Passing behavior reaches `stopping` and then `idle`, releases resistance predictably, and does not require a page reload.

### 9. Control loss

Let a second application request the trainer while the Lab is connected. The ideal FTMS behavior is a Machine Status control-permission-lost event, control `revoked`, and activity `idle`. Some devices may disconnect instead; record that deviation rather than relabeling it as the ideal behavior.

### 10. Competing application isolation

Repeat acquisition with the competing application open and closed. Contention must be visible as a rejection, revocation, or disconnect. Silent simultaneous resistance control is a failure.

### 11. Power-cycle recovery

Stop first, unplug the trainer for 30 seconds, and observe the Lab. Connection must become `disconnected`; telemetry and capabilities must clear. Restore power and connect again without reloading the page.

### 12. Stop under command traffic

At low intensity, submit several target changes quickly and immediately choose **Stop resistance**. Stop must overtake queued targets. No later target may take physical effect and the final activity state must be `idle`.

## Passing, blocked, and unsupported

- **Pass:** all 12 checks succeed, every check contains useful observation notes, and Trainer Lab enables **Export passing report**.
- **Blocked:** the test could not be completed because of browser, firmware, environment, or safety conditions. Preserve the session log and say what blocked it.
- **Unsupported:** the device does not advertise a capability. Do not mark an unimplemented control mode as passed. Open a compatibility report describing the advertised feature bits and stop the release qualification for that configuration.
- **Fail:** a claimed capability returns invalid parameters, times out, produces unsafe resistance, loses stop ordering, or leaves stale state. Do not retry while riding.

## Evidence and privacy

Trainer Lab stores draft metadata and notes in local browser storage for the current runtime. Safety acknowledgement, pass marks, and physical-session counters deliberately reset on reload. Export is enabled only after the current page session and every evidence field pass. The report contains:

- exact non-identifying hardware and client versions;
- the selected resistance encoding;
- source commit and behavioral runtime fingerprint;
- connection, telemetry, response, and error counts;
- one pass/fail result and sanitized observation for every check.

Never include a serial number, Bluetooth address, account identity, precise ride history, access token, or a raw capture containing identifiers. Session logs are debugging artifacts; review and sanitize them before sharing.

Place the exported report in `hardware/reports/`, add the configuration to `hardware/compatibility.json`, and run:

```sh
npm run release:check
```

Then open a **Trainer compatibility report** issue or pull request. A maintainer reviews the evidence; generated JSON is not self-certifying.

## Troubleshooting another trainer

| Symptom                              | Check first                                                | Qualification decision     |
| ------------------------------------ | ---------------------------------------------------------- | -------------------------- |
| No Bluetooth chooser                 | Chrome/Edge, HTTPS or localhost, direct button click       | Blocked environment        |
| Device absent from chooser           | FTMS service advertisement, firmware, other connected apps | Blocked or unsupported     |
| Connect fails during discovery       | Session log; missing Machine Status or advertised range    | Fail strict conformance    |
| `control_not_permitted`              | Close competing controllers, request control again         | Document contention        |
| Resistance returns invalid parameter | Verify `sint16`; try `uint8` only with legacy evidence     | Do not guess by model name |
| Command timeout                      | Stop, disconnect, power-cycle, preserve log                | Fail until explained       |
| Values remain after disconnect       | Library/application stale-state bug                        | Fail                       |
| Unexpected braking or heat           | Cut trainer power                                          | Stop testing               |

When adding support, keep vendor quirks in an adapter or explicit option. Applications should remain capability-driven and should never infer packet layouts solely from a device name.
